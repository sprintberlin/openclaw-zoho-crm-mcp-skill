# Zoho CRM Functions API via MCP

Use this reference to create, inspect, update, publish, and delete Zoho CRM functions with `mcporter` and the Zoho CRM MCP server.

## Required Actions

Enable only the Actions needed for the task:

- `createFunctions`
- `getFunctions`
- `getFunction`
- `getFunctionCode`
- `updateFunction`
- `publishFunction` for Java, Node.js, or Python drafts
- `deleteFunction` only when deletion is explicitly required
- `createCustomButton` when the function must be attached to a module button

Runtime tool names normally have the `ZohoCRM_` prefix. Confirm the live catalog before writing:

```bash
mcporter list "$ZOHO_MCP_URL"
```

Treat `ZOHO_MCP_URL` as a credential and never print or commit it.

## Create a Deluge Function

`createFunctions` accepts function metadata and optional inline Deluge in `_code`. Use the category-specific namespace in the declaration.

```bash
cat > /tmp/zoho-create-function.json <<'JSON'
{
  "body": {
    "metadata": {
      "functions": [
        {
          "name": "Send invitations button",
          "api_name": "send_invitations_button",
          "category": "Button",
          "runtime": "Deluge 1.0",
          "description": "Starts the controlled invitation send.",
          "arguments": [],
          "_code": "string button.sendInvitationsButton()\n{\nreturn \"stub\";\n}"
        }
      ]
    }
  }
}
JSON

mcporter call "$ZOHO_MCP_URL.ZohoCRM_createFunctions" \
  --args "$(< /tmp/zoho-create-function.json)"
```

The MCP server may serialize `body.metadata` as multipart JSON internally. If the live schema expects a JSON string instead of an object, serialize the same metadata object with `json.dumps`; do not remove the `metadata` level.

### Categories and Deluge declarations

| Category | Typical declaration | Use |
| :--- | :--- | :--- |
| `Button` | `string button.sendInvitationsButton()` | CRM custom buttons |
| `Standalone` | `string standalone.sendInvitations(Bool dryRun, Int limit)` | Reuse from other functions or expose as REST/ZAPI |
| `Automation` | `void automation.updateRecord(String recordId)` | Workflow, blueprint, and process automation |
| `Schedule` | Category-specific declaration generated by CRM | Scheduled execution |
| `Related List` | Category-specific declaration generated by CRM | Custom related lists |

The API also advertises `Signals`, `Validation Rule`, and `Dynamic`. Inspect an existing function of the same category or create a UI-generated stub before assuming its signature.

Button functions can be created through `createFunctions`. A button function normally has no custom arguments, so use `"arguments": []` or omit the field. Creating the function does not create or place the module button; that is a separate `createCustomButton` operation or CRM UI step.

## Naming Rules

- `name` is the human-readable display name. Live CRM validation uses `^[A-Za-z][A-Za-z0-9 _-]*$`; punctuation such as a colon is rejected. The name must be unique in the organization.
- `api_name` is immutable after creation. The live schema permits letters, digits, hyphens, and underscores and requires a leading letter. Prefer lowercase letters, digits, and underscores for portable automation.
- The Deluge declaration contains the function's internal script name. It is separate from `api_name`, may use camelCase, and must remain unchanged when updating the code.
- Deluge internal function names are organization-wide within their namespace. Reusing one can produce `COMPILATION_ERROR: Function with name ... exists`.

## Recommended Two-Step Deluge Deployment

A minimal create followed by a full update makes validation failures easier to isolate:

1. Call `createFunctions` with complete metadata and a minimal valid stub.
2. Read the returned function ID from `data.functions[0].details.id`.
3. Call `updateFunction` with the complete source code.
4. Read the code and metadata back before considering the deployment complete.

Direct creation with full `_code` is supported, but the two-step pattern separates metadata errors from full-script compilation errors.

## Update a Function

Use path variable `fxIdentifier`, which accepts the function ID or API name. Keep the `metadata` wrapper:

```bash
cat > /tmp/zoho-update-function.json <<'JSON'
{
  "path_variables": {
    "fxIdentifier": "<FUNCTION_ID_OR_API_NAME>"
  },
  "body": {
    "metadata": {
      "functions": [
        {
          "_code": "string button.sendInvitationsButton()\n{\nreturn \"updated\";\n}"
        }
      ]
    }
  }
}
JSON

mcporter call "$ZOHO_MCP_URL.ZohoCRM_updateFunction" \
  --args "$(< /tmp/zoho-update-function.json)"
```

Do not use this incorrect shape:

```json
{"body":{"functions":[{"_code":"..."}]}}
```

Zoho can return `SUCCESS` and update `modified_time` for that malformed request while leaving the source code unchanged. The response alone is not proof of deployment.

For Deluge, `_code` is auto-published on create and update. `publishFunction` is for Java, Node.js, and Python drafts.

## Verify Every Write

After create or update:

1. Call `getFunctionCode` and compare `data.result` with the local source after normalizing the final newline and insignificant whitespace.
2. Call `getFunction` and verify `state == "active"`, `has_draft == false`, the expected `category`, and the expected `api_name`.
3. Execute a safe dry run or a test record when the function has business side effects.

```bash
cat > /tmp/zoho-get-function.json <<'JSON'
{"path_variables":{"fxIdentifier":"<FUNCTION_ID_OR_API_NAME>"}}
JSON

mcporter call "$ZOHO_MCP_URL.ZohoCRM_getFunctionCode" \
  --args "$(< /tmp/zoho-get-function.json)"
mcporter call "$ZOHO_MCP_URL.ZohoCRM_getFunction" \
  --args "$(< /tmp/zoho-get-function.json)"
```

Back up the current live source with `getFunctionCode` before modifying a business-critical function.

## Attach a Function to a CRM Button

A category-`Button` function appears as an available action, but it is not attached to a module automatically.

- If `createCustomButton` is enabled, inspect its live schema first and supply the target module, placement, profiles/layouts, action type, and function executor required by that schema.
- If the Action is unavailable, use **Setup > Customization > Modules and Fields > [Module] > Links and Buttons** and select the existing function.

List view, detail view, utility menu, layout, and profile visibility are properties of the custom button, not the function itself.

## Expose a Standalone Function as REST/ZAPI

`getFunction` returns `rest_api_mode`, commonly `["None"]` or `["ZAPI"]`. This is a status indicator, not proof that `updateFunction` can change the REST exposure.

If the live MCP catalog has no dedicated REST-exposure Action, enable it in CRM:

1. Open **Setup > Developer Hub > Functions**.
2. Open the function's settings.
3. Select **REST API** / **Invoke as REST API**.
4. Save and verify with `getFunction` that `rest_api_mode` contains `ZAPI`.

Do not place the generated invocation URL or authentication token in a public repository.

## Delete a Function

Use `deleteFunction` only after confirming the function is not referenced by a button, workflow, blueprint, schedule, or another active configuration. Zoho rejects deletion while active references remain.

## Common Errors

| Error | Likely cause | Resolution |
| :--- | :--- | :--- |
| `INVALID_DATA` with a regex for `name` | Unsupported punctuation in the display name | Use letters, digits, spaces, hyphens, or underscores |
| `DUPLICATE_DATA` for `name` | Display name already exists | Reuse the existing function or choose a unique final name |
| `COMPILATION_ERROR: Function with name ... exists` | Deluge declaration collides with another function | Keep the existing internal name during updates or choose a unique one on create |
| `CANNOT_PROCESS` | Ambiguous backend validation failure | Check name/API-name uniqueness, category signature, arguments, and code separately; retry with a minimal stub |
| `SUCCESS` but unchanged source | Missing `metadata` wrapper | Use `body.metadata.functions[0]._code`, then verify with `getFunctionCode` |
